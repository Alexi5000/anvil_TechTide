# Gateway deployment security

The gateway now requires an operator-provisioned bearer token for each device UUID. Configure `ANVIL_GATEWAY_DEVICE_TOKENS` on the server as a JSON object mapping device UUIDs to independent random tokens (at least 32 characters). An empty or invalid mapping denies all registration and stream access. Provision the matching token in the desktop app-data file `gateway-channels/device-token` with owner-only permissions. Never put these tokens in Vite configuration, URLs, source control, or logs. Use HTTPS for all remote gateway traffic. Restart the server when changing its environment; remove a device entry to revoke future requests. Existing open streams require restart to terminate immediately.

Registration and stream acknowledgement are authorized for the named device only. Channel registration returns a random signing secret only to that device. The desktop uses the existing authenticated GitHub CLI to install this secret, including updating existing unsigned hooks during channel hydration. Legacy unsigned channels fail closed until that update succeeds. Channel secrets remain in protected Redis storage and are not persisted in frontend metadata or printed to logs.

Webhook requests require SHA-256 HMAC over the exact received bytes. Valid deliveries enter the stream with atomic Redis deduplication by delivery ID and signed-body fingerprint, retained for seven days. Redis must retain those keys for the full deduplication window; a cleared database or expired record cannot establish historical replay protection. Signature validation does not make webhook text trusted instructions for downstream agents.

Run `TEST_REDIS_URL=redis://127.0.0.1:6379 pnpm --dir server test` against an isolated Redis instance. Tests create synthetic device, channel, stream and deduplication keys. CI supplies a dedicated Redis service. Production gateway provisioning, live GitHub delivery and desktop/native verification are separate deployment checks.
